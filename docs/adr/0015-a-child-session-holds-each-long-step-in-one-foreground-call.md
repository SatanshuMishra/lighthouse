# A child session holds each long step in one foreground call

Status: accepted; supersedes the hold by completion notice in ADR-0012 for the child session

`lighthouse launch` starts the child session with the Bash tool's longest timeout set to one week, and the child runs every long step, the suite, the acceptance checks and a profile measure, as one foreground Bash call that asks for that timeout, so the call returns only when the step ends. ADR-0012 held a long step by its completion notice, which was shown on a session without a reply schema. ADR-0014 then gave the child a reply schema, and a session with one is asked for its structured reply the moment a turn ends. The only reply the schema admits is a verdict, so the first 0.8.0 child that ended a turn to wait for a profile measure released its worktrees and returned a blocked verdict 12 seconds after starting the step. On Claude Code 2.1.318 the Bash tool also caps a call's timeout at ten minutes, moves a foreground call to the background when its timeout passes, and stops a call it moved ten minutes after that, so a step over twenty minutes could not be held either way under the tool's own ceilings.

The Bash tool's default timeout stays two minutes, and launch drops a default it inherits from its caller. That default is the only thing that frees a session from a quick command that hangs: of 188 calls the tool moved to the background in this machine's recorded run sessions, 85 were not test runs, among them reads of standard input, walks of the whole disk and git and grep calls that never returned. In a probe, a session with both timeouts raised that started a server in the foreground was still held when the probe ended it at 420 seconds; the same session with only the longest timeout raised had the server moved after two minutes and finished in 141 seconds. A 660 second step run with the one-week timeout under the raised longest timeout alone was held in one call, in 4 turns, and nothing was moved.

No wall-clock limit comes back: one week is the Bash tool's ceiling raised out of the way, not a limit lighthouse reads or judges by. A long step the child runs without the timeout argument is moved after two minutes like any other command, and the skill tells the child to stop it by its id and run the step again with the timeout. The session a person starts still holds `lighthouse launch` by its completion notice, because it has no reply schema and lighthouse does not start it.

## Considered options

- Raising the default timeout as well, so the child needs no timeout argument: the first version of this change did it, and the probe above showed a foreground server then holds the session with nothing to move it.
- Keeping the completion notice and adding a reply form that means still waiting: a session with a schema was shown to wait and reply again after the notice, but it needs a schema change the program owns, costs a forced reply at every hold, and leaves a destructive reply one misreading away.
- Foreground holds in fixed windows that the session calls again and again, as before ADR-0012: needs no raised ceiling, but turns every hold into polling, 7 turns for a 150 second step in the probe against 4 for a 660 second step held in one call.
- Dropping the reply schema: brings back reading the verdict from prose, which ADR-0014 removed for losing findings.
