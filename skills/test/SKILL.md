---
name: test
description: Use when a FEATURE branch holding merged changes must be proven before it merges into its core branch, for any kind of software. Runs the project's own suite on both branches, drives the running product the way a person or calling program uses it, rechecks the surfaces next to the change, has the lighthouse command compute the verdict, and opens the FEATURE pull request on green or with --final. Takes --repo, --core, --feature, --results, --previous, --spec and --final, and ends with one JSON verdict line. The work runs in a child claude -p session in bypassPermissions mode, started from the results folder.

# lighthouse:test

Prove the FEATURE branch works: its suite, its new behaviour as used, and its neighbours. Report what was found; the lighthouse command computes the verdict.

## Inputs

- `--repo <path>`: the repository under test.
- `--core <branch>`: the core branch, the long-lived branch the repository ships from.
- `--feature <branch>`: the FEATURE branch holding the merged changes under test.
- `--results <dir>`: the results folder this run writes into.
- `--previous <dir>`: an earlier results folder for the same FEATURE branch, never the same folder as `--results`; this run retests only what failed there and what new commits touched.
- `--spec <path>`: the spec, when one exists.
- `--final`: open the pull request whatever the verdict, listing every failure as unresolved.
- `--child`: the flag `lighthouse launch` passes to the child session it starts; a person never passes it.

`lighthouse` in this skill always means `${CLAUDE_PLUGIN_ROOT}/bin/lighthouse`: run it by that full path, written out in each command, never a `lighthouse` found on PATH, which may be an older installed copy.

Everything a run needs from lighthouse is in this skill and in what its commands print, including their refusals: never read lighthouse's own code, profile schema or README, and never run its `--help`. The Command reference below names every subcommand this skill runs, its flags and the keys of the JSON it prints.

## Launch

Without `--child`, do only this, so the calling session never carries the run's work:

1. Start `lighthouse launch <the flags you were given> --repo <repo>` in the background, with run_in_background. It starts the child session with `--child` and the same flags, keeps the machine awake while it runs, and writes the child's verdict line to `<results>/launch.json`.
2. Run `lighthouse wait --until 'test -s <results>/launch.json'` in the foreground, with the Bash tool's timeout set to 600000 ms, because its 120000 ms default is shorter than the wait's 540-second window and a call that outlives it is moved to the background instead of returning ready false. Each time it returns with ready false, call it again, the same way, until it returns ready true. A headless session ends while a background command still runs, so never wait for a completion notice instead.
3. When that line's verdict is blocked, say in one line the reason `lighthouse launch` printed, its `error` or its `blocked:` summary, read from the background command's output. Print the line in `<results>/launch.json`, unchanged, as the last line of the reply. `lighthouse launch` has already appended the run to the ledger, so never run Stopping early for it.

When `lighthouse launch` ended without writing `<results>/launch.json`, such as when it refused a results folder inside the checkout, stop as Stopping early says, with its reason.

With `--child`, run the Steps below.

## Steps

Around each step below, run `lighthouse mark --results <results> --step <name> start` before it and the same with `end` after it, naming the step worktrees, retest, profile, change, suite, build, drive, spend, verdict, pr or release; mark the build step once per build with `--build core` or `--build feature`. Write the first mark only after step 1's checks pass, since a mark writes into `<results>`. Run a start mark in the same Bash call as the first command it marks, joined by && or ;, and the end mark in the same call as the last, always after ;, so a failing command never skips the end mark of what it failed: never a mark in a Bash call of its own. For example: `lighthouse mark --results <results> --step change start && lighthouse change --repo <repo> --core <core> --feature <feature>; lighthouse mark --results <results> --step change end`. A mark around an action that is not a Bash call, such as a driver dispatched through the Agent tool, a skill such as lighthouse:init or the pull request tool, rides in the nearest Bash call before or after that action.

1. Note the start time as UTC ISO-8601 and the untracked paths of the checkout at `--repo` from `git -C <repo> status --porcelain --untracked-files=all`. When `--results` is inside that checkout, stop before writing anything, as Stopping early says, with the reason that the results folder must be outside the checkout. When `--previous` names the same folder as `--results`, stop the same way, with the reason that `--previous` must name a folder other than `--results`.
2. Run `lighthouse worktrees --repo <repo> --core <core> --feature <feature> --results <results>`, marked as the worktrees step. It checks out both tips at `<results>/core` and `<results>/feature`, and refuses with exit 2 a results folder inside the repository; on any refusal, stop as Stopping early says, with its reason.
   - When `--previous` is given, run `lighthouse retest --previous <dir> --results <results> --repo <repo> --core <core> --feature <feature> --profile <results>/feature/.lighthouse/profile.json`, marked as the retest step, and keep its plan: `full`, `changed`, `retest`, `surfaces` and `carried`. It writes the same plan, with `carried_paths`, to `<results>/retest.json` and copies each carried path's evidence under `<results>/previous/`.
3. Run `lighthouse profile check --repo <results>/feature`, marked as the profile step with the rest of this step.
   - When a problem has kind `missing`, invoke lighthouse:init `--unattended --repo <results>/feature`. On any other problem, invoke lighthouse:doctor `--unattended --repo <results>/feature`. Then run the check again.
   - When the check passes and lists upgrades, invoke lighthouse:doctor `--unattended --repo <results>/feature` once for them and carry on whatever it does; upgrades never block the run and never stop it.
   - When it still fails, record the suite as `{"result": "blocked", "reason": "profile: <problems>", "failures": [], "pre_existing": [], "flaky": [], "core": null, "feature": null}`, the build as `{"result": "blocked", "reason": "profile"}` and no paths, and go to step 8.
   - Otherwise run `lighthouse profile publish --repo <repo> --feature <feature> --profile <results>/feature/.lighthouse/profile.json`. It folds every stored answer in and commits only when the profile changed. When its JSON says `committed` is true, run `lighthouse worktrees` again with the same four flags, so `<results>/feature` moves to the new tip and holds the answered facts. When publish exits non-zero, carry on and keep its reason for step 12.
   - Then copy `<results>/feature/.lighthouse/profile.json` to `<results>/profile.json`. This copy is the run's profile: every later `--profile` names it, because `lighthouse suite` resets `<results>/feature` to the branch tip and would discard a repair that was not published.
4. Run `lighthouse change --repo <repo> --core <core> --feature <feature>`, marked as the change step, for the commits, the changed files and the merged pull requests. Then run `lighthouse suite --repo <repo> --core <core> --feature <feature> --results <results> --profile <results>/profile.json`, marked as the suite step, and keep its JSON object as the suite.
5. Plan the paths. Nothing else is tested.
   - With `--previous`: when the plan's `full` is true, or `lighthouse retest` exited non-zero (say why), plan every path as without `--previous`, by the rules below. Otherwise plan only the plan's `retest` paths, the new-behaviour and neighbour paths of its `surfaces`, and the one-hop neighbours of the changed files in its `changed` list, found as the Neighbours rule below finds them but from those files rather than the whole change. `lighthouse suite` reuses core's stored result when core's commit and the profile's setup, build and suite commands match an earlier run, so a retest on an unmoved core never runs core's suite again, while FEATURE's suite always runs.
   - Every name in the plan's `retest` list is a planned path, whether `full` is true or not: drive each one again and record it in `findings.json` under exactly that name, never renamed, merged with another path or split into several, and add any fresh path beside them under a name of its own. A carried path driven again keeps its name too.
   - New-behaviour paths: one product path for each thing the change adds, with its expected outcome, from the spec's intent and acceptance criteria when `--spec` is given, otherwise from the merged pull requests' titles and bodies and the commit messages. Name each path for the behaviour it checks in the words the spec, the merged pull requests and the commits use for it, so the name under failures or unproven tells a reader what broke or went unchecked without opening the report; a planned retest path still keeps exactly its name.
   - Neighbours: each profile surface whose recorded `paths` include a changed file, or a file that uses something the change altered. Go one hop only. Use `graphify-out/graph.json` when the repository has one, otherwise a text search of `<results>/feature` for the altered names. Name each neighbour path the same way, for the behaviour it checks in the words the change itself uses.
   - In a Claude Code plugin, a live session decides which skill, agent, command or MCP tool handles a request by reading all of their names and descriptions together, and fires each hook by its event and matcher, as the plugin manifest and component files declare them. So when the change alters any of those names, descriptions, matchers, events or manifest entries, every other component of the plugin that a session could pick in place of the changed one, or that fires on the same event, uses what the change altered: it is a one-hop neighbour, and so is the changed component.
   - Choose each path's check: the lightest of suite, direct and drive that still observes the expected outcome on the surface the intent names. suite: named tests in the project's suite assert the outcome and passed on FEATURE, and on core too for a neighbour; use it only when the suite writes a JUnit report. direct: an HTTP or command-line call whose response holds the outcome. drive: the surface's recorded driver, when the outcome is what a person sees or which component a model chose. A new-behaviour path whose intent names something seen on screen uses drive. Write its why naming the assertion or observation that shows the outcome, and its tests naming the test ids for a suite check, otherwise empty.
6. Build and start each build in its own worktree, `<results>/core` and `<results>/feature`, with the profile's `setup`, `build` and `start` commands, giving each build its own ports and data and setting `LIGHTHOUSE_BUILD` to `core` or `feature`, each marked as the build step with its `--build`. Run each build's start command with its output written to `<results>/<build>-start.log`, `<build>` being core or feature, as `<start command> > <results>/<build>-start.log 2>&1`, so a log-line ready check has a file to read. Wait for `start.ready` with `lighthouse wait --until '<the ready check>'`, the ready check built from `start.ready` as the Command reference says, run with the Bash tool's timeout set to 600000 ms, calling it again each time it returns ready false.
   - When FEATURE will not build or start after two tries, record the build as `{"result": "blocked", "reason": "<the failing step>; core built"}` or `"...; core did not build"`, and test no product path on it. Otherwise record `{"result": "ok", "reason": null}`.
   - Sign in only through `lighthouse with-credentials --repo <repo> --profile <results>/profile.json --cwd <that build's worktree> -- /bin/sh -c '<the surface's sign_in command>'`, so the run's profile decides which entries are production and which credentials file is read.
   - A path is unproven, with its reason, when its surface is unavailable (`available` false), rests on an unconfirmed fact, needs an action the profile lists as off-limits, or cannot be signed into.
7. Prove each path by its check, all of it marked as the drive step. A suite path is proven by the suite step's result: record `suite.json` as its evidence and its `retry`, `core` and `trials` as null. Make a direct path's call yourself and a drive path's through the driver. Dispatch every driver through the lighthouse:driver agent, giving it the absolute path of the lighthouse command, `${CLAUDE_PLUGIN_ROOT}/bin/lighthouse` with that folder written out, the paths, the surface's recorded `driver`, the build, `<results>`, where to save evidence and the mark commands to run. Save every screenshot, transcript, response and output under `<results>/evidence/`, and record each as a path relative to `<results>`.
   - Every driver, and you for a direct call, runs `lighthouse mark --results <results> --step drive --build <core or feature> --path '<path name>' start` before driving each path and the same with `end` after it. A driver that starts `claude -p` trial sessions for a path adds `--folder <the folder they start in>` to that path's start mark. Each runs a start mark in the same Bash call as the first command it marks, joined by && or ;, and the end mark in the same call as the last, always after ;, never a mark in a Bash call of its own; the drive step's marks around a driver dispatched through the Agent tool ride in the nearest Bash call before or after that dispatch.
   - Start every driver, browser and tool session from the working folder `<results>/work`, and point any browser tool's output and screenshot folder at `<results>/evidence/`. Never drive with a tool whose output lands in the checkout at `--repo`.
   - A new-behaviour path runs on FEATURE and is judged against the intent. Its `core` is null.
   - A neighbour gets the same probe on core and on FEATURE. A difference the intent does not explain is a failure. A difference the intent explains is expected: write that outcome as `expected`, mark it passed and note the difference in its evidence.
   - Retry each failure once on FEATURE and record the second outcome as `retry`, otherwise null. Probe a failing neighbour on core and record that as `core`.
   - Reach a Claude Code plugin path only through a live Claude Code session that loads that build's copy of the plugin and no other copy of it, such as `claude -p` with `--plugin-dir` set to that build's worktree and an output format that records every tool call, started from a working folder under `<results>` prepared the same way for both builds. Send what a person would send: a plain request for the outcome, phrased from the intent and never copied from a component's own description, naming a component only where people name it, such as a slash command, and doing the thing that fires a hook. Reading a component's files, running its scripts on their own or naming a skill or agent a person would not name skips the session's choice, so it never reaches the path; when the recorded `driver` works that way, keep it only as an extra check.
   - The observable outcome of a plugin path is which component handled the request, read from the saved transcript (the skill, agent, command, MCP tool or hook that ran), and what that component produced or changed. A path passes only when the component the intent names handled it and its outcome matches; a request handled by another component, or by none, fails even when the reply reads well. A neighbour gets the same requests on both builds, and a request core sends to one component and FEATURE sends to another is a difference the intent must explain.
   - A plugin path goes through a model's choice even when the component's own output is fixed, so it is model-driven: run it with the surface's `trials` when above 1, otherwise 3, using the same requests on both builds.
   - When the surface's `trials` is above 1, or the rule above sets 3, run each case that many times on each build, graded on the outcome, never on wording. Record `trials` as `{"count": <n>, "feature_passed": <n>, "core_passed": <n or null>}`, and status passed only when every FEATURE trial passed. Otherwise `trials` is null.
   - Hold for a condition, such as a build, a server, a VM or a driver's result, only with `lighthouse wait --until '<check>'`, run with the Bash tool's timeout set to 600000 ms, calling it again each time it returns ready false. Never use a blind sleep.
   - An environment problem you cannot fix, such as a throttled VM or a sleeping host, leaves its paths unproven with that reason; record it and carry on with the other paths.
8. Run `lighthouse spend --since <start time> --results <results> --repo <repo>`, marked as the spend step, and keep its `tokens`, `minutes` and `dollars`. It writes `<results>/spend.json`.
9. Write `<results>/findings.json`:
   ```json
   {"version": 1, "suite": <lighthouse suite's object>, "build": {"result": "ok", "reason": null},
    "paths": [{"name": "...", "kind": "new" or "neighbour", "surface": "...", "expected": "...",
               "evidence": ["evidence/..."], "status": "passed" or "failed" or "unproven",
               "retry": "passed" or "failed" or null, "core": "passed" or "failed" or null, "trials": null,
               "check": {"kind": "suite" or "direct" or "drive", "why": "...", "tests": ["..."]}}],
    "spend": {"tokens": <n>, "minutes": <n>, "dollars": <n or null>}}
   ```
   Every path driven in this run records its check; `lighthouse verdict` verifies a suite check's tests against what `lighthouse suite` recorded, never against these findings.
   With `--previous`, `paths` holds the paths driven in this run plus every entry of `<results>/retest.json`'s `carried_paths`, copied unchanged, except that a carried path also driven in this run appears once, with its new result replacing its copy. `lighthouse verdict` lists as unproven any planned retest path left out of `paths`, or whose evidence names no existing file of this run outside `previous/`, so record each driven path's fresh evidence under `evidence/`. It matches each name exactly, so a retest path driven under any other name still counts as left out.
   Then run `lighthouse verdict --results <results> --repo <repo>`, marked as the verdict step. It writes `report.md` and `verdict.json`, appends the run to the ledger in the state folder, and prints the verdict line. Never write or change a verdict yourself.
10. When the verdict is green, or `--final` is given, run `lighthouse pr --repo <repo> --core <core> --feature <feature> --results <results> --summary '<a lowercase summary of the feature>' --why '<the intent>'`, adding `--final` when given, marked as the pr step with the opening below. When the repository's remote is on GitHub, open the pull request with its `title`, `body`, `base` and `head`, ready for review and never a draft: through the GitHub MCP `create_pull_request` tool when this session has it, otherwise `gh pr create --base <core> --head <feature> --title '<title>' --body-file <results>/pr-body.md` after writing the body there. With any other remote, open nothing and say why.
11. Run `lighthouse release --repo <repo> --results <results>`, marked as the release step. Then compare the checkout's untracked paths with those noted in step 1, and name every path that appeared during the run in the reply as a change to the checkout. Move, delete or edit nothing in the checkout: a new path may be the person's own work.
12. When publish exited non-zero in step 3, say in one line that the profile was not published and why. Print the verdict line from `<results>/verdict.json`, with `pr` set to the pull request's URL or null, as the last line of the reply, one JSON object on one line:
    `{"verdict": "green", "failures": [], "unproven": [], "flaky": [], "tokens": 0, "minutes": 0, "dollars": 0, "pr": null}`

## Stopping early

Every stop before step 9 ends the same way: say the reason in one line, run `lighthouse verdict --blocked '<that reason>' --repo <repo> --results <results>`, and print its line, `{"verdict": "blocked", "failures": [], "unproven": [], "flaky": [], "tokens": 0, "minutes": 0, "pr": null}`, as the last line of the reply. With `--blocked`, `--results` only names the run: nothing in the results folder is read or written, so the reply still ends in the verdict line a caller reads, and the ledger keys the stop to the same run as its launch line.

## Cost

Scope comes from the change: the new-behaviour paths and their one-hop neighbours, nothing else. Each path gets the lightest check that still observes its outcome, one probe and at most one retry, or its trials. The project's own suite runs first, core's stored result is reused when nothing it depends on moved, and doctor runs only when the check fails or lists upgrades. Cost is cut by fitting checks and removing waits, never by narrowing scope.

## Never

- Never ask anything; init and doctor run with `--unattended`.
- Never narrow scope to save time: drop no planned path, surface or trial for time or cost. What cannot be reached is unproven, with its reason.
- Never hold with a blind sleep; hold only with `lighthouse wait`.
- Never fix code, never merge, and never touch the checkout at `--repo` or anything the profile lists as off-limits. The profile commit from `lighthouse profile publish` is the only write to the project.
- Never read, print or pass a credential value; only `lighthouse with-credentials` puts values into a process.
- Never add a tool or dependency to the project.
- Never count an unreached path as passed; it is unproven.

## Command reference

Each line names a subcommand, every flag it accepts and what that flag means, and the keys of the JSON it prints. A refusal exits 2 and prints `{"error": <reason>}`, which names what to change.

- `lighthouse launch`: `--repo <path>` the repository under test; `--core <branch>` the core branch; `--feature <branch>` the FEATURE branch; `--results <dir>` the results folder; `--previous <dir>` an earlier results folder to retest from; `--spec <path>` the spec; `--final` open the pull request whatever the verdict. Starts the child session and prints its verdict line, with keys `verdict`, `failures`, `unproven`, `flaky`, `tokens`, `minutes`, `dollars` and `pr`, also written to `<results>/launch.json`.
- `lighthouse wait`: `--until <check>` the shell command that passes once the condition holds; `--every <seconds>` how often to run the check, 5 by default; `--within <seconds>` how long to keep checking, 540 at most and by default. Run it with the Bash tool's timeout set to 600000 ms. Prints `ready`, true when the check passed and false when the window ran out, and `seconds`, how long it waited.
- `lighthouse mark`: `--results <dir>` the results folder whose `marks.jsonl` it appends to; `--step <name>` the step; `--build core|feature` the build; `--path <name>` the product path; `--folder <dir>` the folder a path's `claude -p` trial sessions start in; then `start` or `end`. Prints the line it wrote: `step`, `build`, `path`, `folder`, `edge` and `time`.
- `lighthouse worktrees`: `--repo <path>` the repository; `--core <branch>` and `--feature <branch>` the two tips to check out; `--results <dir>` the results folder that holds them. Prints `core` and `feature`, each with `path` and `commit`.
- `lighthouse retest`: `--previous <dir>` the earlier results folder; `--results <dir>` this run's results folder; `--repo <path>` the repository; `--core <branch>` and `--feature <branch>` the branches; `--profile <file>` the profile whose surfaces it reads. Prints `full`, `changed`, `retest`, `surfaces` and `carried`, and writes the same with `carried_paths` and `previous` to `<results>/retest.json`.
- `lighthouse profile check`: `--repo <path>` the repository; `--profile <file>` a profile other than the repository's own. Prints `ok`, `problems`, each with `kind` and `detail`, and `upgrades`, each with `field` and `detail`; exits 1 when there are problems.
- `lighthouse profile publish`: `--repo <path>` the repository; `--feature <branch>` the branch to commit the profile to; `--profile <file>` the profile to publish. Prints `committed`, and `commit` when it is true.
- `lighthouse change`: `--repo <path>` the repository; `--core <branch>` and `--feature <branch>` the branches to compare. Prints `core`, `feature`, `core_commit`, `feature_commit`, `commits`, each with `sha`, `subject` and `body`, `files`, `pull_requests` and `pull_requests_error`.
- `lighthouse suite`: `--repo <path>` the repository; `--results <dir>` the results folder; `--core <branch>` and `--feature <branch>` the branches; `--profile <file>` the run's profile. Prints `result`, `reason`, `failures`, `pre_existing`, `flaky`, `core` and `feature`, and writes the same to `<results>/suite.json`.
- `lighthouse with-credentials`: `--repo <path>` the repository; `--profile <file>` the profile that names the credentials; `--cwd <dir>` the folder to run in; then `--` and the command. Runs the command with the credentials set and prints what it prints, with every value hidden, exiting with its code.
- `lighthouse spend`: `--since <time>` the UTC ISO-8601 start time; `--from <dir>` the folder whose sessions to count when no `--results` is given; `--transcripts <dir>` a transcripts folder other than Claude Code's own; `--results <dir>` the results folder whose sessions and marks it reads; `--repo <path>` the repository, which writes `<results>/spend.json`; `--prices <file>` a price table other than lighthouse's own. Prints `tokens`, `minutes` and `dollars`, the token kinds `input`, `cache_write_5m`, `cache_write_1h`, `cache_read` and `output`, and `messages`, `models`, `unpriced`, `expired_rewrites`, `waiting`, `steps`, `paths` and `shared`.
- `lighthouse verdict`: `--results <dir>` the results folder whose `findings.json` it judges; `--blocked <reason>` the reason a run stopped early; `--repo <path>` the repository whose ledger it appends to. Prints the verdict line: `verdict`, `failures`, `unproven`, `flaky`, `tokens`, `minutes`, `dollars` and `pr`, and writes `report.md` and `verdict.json`.
- `lighthouse pr`: `--repo <path>` the repository; `--core <branch>` the base; `--feature <branch>` the head; `--results <dir>` the results folder; `--summary <text>` the title's summary; `--type <type>` the title's change type, feat by default; `--scope <scope>` the title's scope; `--why <text>` the intent; `--final` compose it whatever the verdict. Prints `title`, `body`, `base` and `head`; exits 1 and prints nothing when the verdict is not green and `--final` is not given.
- `lighthouse release`: `--repo <path>` the repository; `--results <dir>` the results folder whose worktrees it removes. Prints `removed`.

Step 6 writes each build's start output to `<results>/<build>-start.log`. Each kind of `start.ready` becomes the check `--until` takes: a URL as `curl -fsS <url>`, a log line as `grep -qF '<line>' <results>/<build>-start.log`, and a command as itself.
